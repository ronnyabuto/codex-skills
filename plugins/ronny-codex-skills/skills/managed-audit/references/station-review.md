# Role-aware station review

## Orientation

Map the actual customer journey and station transitions, role ownership, permissions and information flows. Record uncertainty about operational practice and ask the user or an authorized staff source to resolve it. Specialist agents can assess staff perspectives; they cannot stand in for staff interviews.

Inspect each crucial role's rendered dashboard using available browser tools before judging that role's experience. Source code can explain what is rendered but does not establish that the live experience works. Record account role, route, environment/revision where available and the state observed. If access or rendering is blocked, disclose the gap and avoid claiming a live review.

If the user requests an end-to-end client journey, first do an orientation walkthrough with a designated demo/test client, then deepen the audit one station at a time. Coordinate login changes and browser state through the manager so workers do not alter each other's sessions. Use independent sessions where available and appropriate.

Account resets, 2FA changes, client selection and production actions require task-specific authorization, which can already be present in the prompt. Act within that established scope without asking again. Clarify only uncertain account/environment identity or consequential operations outside it. Do not generalize permission for demo-account resets to other users, projects or future audits.

## Review the current station

For each involved role, establish what they need to know, decide and do. Examine visibility, action placement, urgency cues, missing context, redundant information and handoff ownership. Check both what a role can see and what it should be able to see; a clean dashboard is not proof of backend authorization.

Select realistic scenarios based on product behavior and risk: normal completion, missing/incorrect data, delays, duplicates, reassignment, cancellation, retries, interrupted work and permission boundaries. Explain consequential gaps; do not turn a simple station into an exhaustive combinatorial test suite.

Prioritize improvements by demonstrated user/operational value. Distinguish a real need from a preference, propose the smallest adequate solution and explain tradeoffs. For a defensibility hypothesis, name the distinctive capability, benefiting customer, supporting evidence and a way to validate the advantage. More features or dashboards alone do not establish differentiation.

## Station result

Provide the observed workflow and role-specific evidence; concrete problems and consequences; a few prioritized improvements; the simplest implementation direction; and verification criteria. Link relevant artifacts rather than dumping logs. Keep unverified hypotheses separate from confirmed findings. Ask decision-changing questions before finalizing recommendations. Complete the requested discussion before moving to the next station; implementation remains governed by the user's authorization.
